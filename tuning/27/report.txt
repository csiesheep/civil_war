#27 機制 B 第二張:bot 學會圍點打援(零和賽局),B 開 vs B 關
================================================================

分支 be/27-bot-b。普通對普通、cell full,每批 1000 局。數字全部從 tuning/27/runs/ 的狀態檔讀出來
(node tuning/27/report.mjs 印出本檔下半部的表;本檔上半部是我的讀法,表是證據)。

怎麼跑的
- B 關:預設規則,`node tests/sim.js 1000 --cell=full --seed=S --jobs=28`。
- B 開:同樣再加 `--variant=B`(tuning/23/variants.mjs 的 B = `{ mechanismB: true }`)。
- 種子 S = 1、20001、40001。六批由 tuning/27/runall.sh 依序跑(B 關、B 開交錯),每批跑完接著
  `node tests/targets.mjs <state.json>`(輸出在 tuning/27/runs/*.targets.txt)。
- B 的數字由 tests/sim.js 的 `playGame` 記在 `more`(和 `rec` 並排,因為 `rec` 與 `summarize` 的形狀
  tests/sim.test.js 鎖住了),`moreStats` 加總,狀態檔放在 `cells.full.more`;`cells.full.sum` 和以前一樣。
  記法:國軍被問的那一刻讀 pending 的選項(可不可以增援 / 突圍);不能增援時分原因:T 是孤城(引擎整個
  不給增援)> 沒有 R(照引擎 reinforceSources 的條件在 sim.js 重讀一次;引擎沒有匯出)> 有 R 但 T 滿了
  (上限 − 藍 = 0)。三者都不是的計成「讀不出原因」——六批都是 0,這是 sim.js 的讀法和引擎一致的證據。
  格子、−1 / +1、圍城、進剿從 log 讀;「只因圍城而在結算掉的藍」= 結算開始時(probe.home "turnEnd")
  有圍城標記而補給仍然到得了的城,在接下來的 attrition 裡掉的藍。純策略 = mix 最大的一格 ≥ 0.999。
- 每局秒數:六批是依序跑的,中間機器的負載變了(B 關 s1、s20001 是 8.6 秒,B 關 s40001 是 14.9 秒,
  同一份程式、同樣 28 個 job),所以六批的秒數不能互比。另外用 tuning/27/runpair.sh 讓 B 關與 B 開
  同時跑種子 1..1000、各 14 個 job(第 5 節),並排的兩批和第 0 節的 s1 兩批 sum 一模一樣(同樣的對局)。

B 關掉時不變
- 三批 B 關的 `cells.full.sum` 和 tuning/24/runs/default-s{1,20001,40001}.txt.state.json 的(鍵排序後)
  一模一樣,errors 都是 0(第 0 節)。
- 開工時另外在 origin/main(124da55)與分支各跑 `--seed=1` 200 局,sum 一模一樣;比較用的腳本拿
  1000 局對 200 局比會說「不同(257 個葉子)」,所以它會紅。
- fuzz 的動作數 266463(FUZZ-VERDICT),和以前一樣。

評估:沒有改。B 開著時我沒有改 `evaluate` 的任何一項(見下面「為什麼幾乎都是純策略」:圍城的價值
評估算得到,一格一格拆過)。

一、勝率、結束方式、結束回合(第 1、2 節)
----------------------------------------------------------------
- 十項目標:六批都是 8 / 10,通過與失敗的是同樣的八項與兩項(「每回合孤城數逐回合上升」與「支持度軌
  照腳本」B 關就不過,B 開也不過;停損兩項都過)。B 沒有讓任何一項換邊。
- 共軍勝率:B 關三批 62.8% [61.1, 64.5](626..631 勝 / 1000),B 開三批 59.6% [57.9, 61.4]
  (580..607 / 1000)。B 開讓共軍少贏約 3 個百分點,兩個區間不重疊;每一批也都是 B 開比較低
  (s1 63.1 → 60.2、s20001 62.7 → 58.0、s40001 62.6 → 60.7)。
- 結束方式:B 開時整編(國軍)多 2 到 5 個百分點(19.5–21.6% → 23.2–25.0%),易幟少一點
  (11.1–13.1% → 8.2–10.9%),民心大致一樣(41–47% → 40–42%)。陝北遷都從 35% 降到 30%。
- 結束回合:分佈幾乎不動;第 5 回合結束的多 1 到 3 個百分點。
- 離群:B 開有 2 局以「記分卡」結束(s1、s40001 各 1;B 關 0)。B4 的上限(≤ 1 局)只在 B 關的
  普通對普通驗;這兩局我沒有追,寫在「沒驗到」。

二、B 的數字(第 3 節;B 開三批,共 3000 局)
----------------------------------------------------------------
- 共軍每局打城 3.15 次(中位 3,最多 12;3.6% 的局一次都沒打)。三批的平均 3.13–3.18,很穩。
- 打點 88.4%、打援 11.6%。
- 國軍被問 9449 次:可以增援的只有 118 次(1.2%);可以突圍 76.0%;只能固守 24.0%。
  不能增援的原因:T 是孤城 25.0%、沒有 R 25.6%(其中 1432 次 T 也滿了)、有 R 但 T 滿了 48.1%。
  → 筆記的「滿編收不了援軍那條會不會太狠」:是,而且是最主要的一條。T 不是孤城、也有 R 的詢問裡,
     97.5% 被「T 滿了」擋掉(4548 次 vs 可以增援的 118 次);把沒有 R 而 T 也滿了的 1432 次算進來,
     至少 63% 的詢問裡 T 是滿的(孤城那 25% 沒有讀滿不滿)。
- 國軍實際的回答:固守 72.3%、突圍 27.1%、增援 0.6%(52 次)。
- 六格:打點/固守 63.9%、打點/突圍 24.1%、打援/固守 8.4%、打援/突圍 3.0%、打點/增援 0.4%、
  打援/增援 0.2%。
- −1(打點遇增援、X 被抵銷到 0):32 次;+1(打援遇增援):18 次。
- 圍城標記(打援遇固守):796 個;其中 674 次在結算時那座城只因為標記而成孤城,因此掉了 750 點藍
  (每局 0.25 點)。
- 純策略:共軍的打城決定 88.7%、國軍的回答 91.7%(9449 個決定,每個都帶 game)。
- 進剿:共軍守 92.7%、撤 7.3%(51081 次)。

有沒有哪一格永遠最好(筆記第 1 批的問題)
- 幾乎是:打點 / 固守。在 30 局(種子 1..30)的探針裡,共軍 95 個矩陣中有 68 個是打點每一行都不輸
  打援(打援每一行都不輸打點的只有 3 個);國軍只能固守的 20 個全是純策略,有突圍可選的 74 個裡
  純策略 64 / 66(共軍 / 國軍)。
- 為什麼:打援只在國軍「增援」時有用(拿走 R 的藍、共軍 +1),而增援只在 1.2% 的詢問裡可以選
  (上面那條「T 滿了」)。剩下打援只換到一個圍城標記:結算時那座城算孤城(掉 1 或 2 點藍)、
  那一回合不能扶植、下一次打它 +1;打點則是當場拿掉 X 點藍。X ≥ 1 時打點通常就比較好。
- 我拆過一個「打點/固守 = 打援/固守」的矩陣(種子 4 第 4 回合打南京,X = 1、藍 4):那是這一回合
  最後一個行動,模擬一路結算到下一回合;打援/固守的圍城讓南京在結算掉 1 點藍,剛好等於打點拿掉的
  X = 1。評估看得到圍城(isolatedAttrition / isolatedNoPlace 兩項),所以我判斷純策略多是規則造成的,
  不是評估錯了,沒有改評估。如果 owner 想讓打援有用,要動的是規則(例如增援不受 T 的上限擋、或
  圍城的代價),不是 bot。

三、孤城(第 4、5 節)
----------------------------------------------------------------
- 「第一座孤城出現在第幾回合」照 tests/sim.js 原本的讀法(rec.firstIsolated:任何一個時刻有一座城
  斷了補給)兩邊都是 99.9–100% 在第 1 回合——這個讀法在這裡分不出東西。所以我加了「第一個回合末
  有孤城的回合」(more.firstIsolatedEnd,並排的兩批,種子 1..1000):
  B 關 第 1 回合 36.9%、第 2 回合 40.1%、第 3 回合 10.8%、第 4 回合 10.0%、更晚 1.9%、沒有 0.3%;
  B 開 第 1 回合 42.5%、第 2 回合 36.5%、第 3 回合 12.3%、第 4 回合 8.0%、更晚 0.6%、沒有 0.1%。
  中位都是第 2 回合。B 讓第一座孤城早一點(第 1 回合多 5.6 個百分點)。
- 「國軍是不是第 3 回合就被切碎」:不是。第 3 回合末的孤城數 B 關平均 1.74、B 開 1.75(各 2998 局);
  ≥ 3 座 21.3% → 22.8%、≥ 5 座 12.1% → 10.6%;三批之間的差和 B 開關的差一樣大。逐回合的平均也幾乎
  一樣(第 1 回合 1.06–1.22 → 1.24–1.28 稍多,第 6 回合 4.5–4.6 → 4.3–4.4 稍少)。

----------------------------------------------------------------
五、bot 怎麼做的(public/shared/bots.js)
----------------------------------------------------------------
- `zeroSum(M)`:兩列(或兩行,轉成 −Mᵀ 解)的零和賽局。f(p) = min_j(p·a_j + (1 − p)·b_j) 是凹的,
  最大值在 p = 0、1 或兩條線的交點,全部列舉;行方的策略從在 p* 打到值的那幾行取(p* = 0 取斜率
  最小、p* = 1 取最大、內部有平的取平的,否則一升一降混成讓列方無差異)。拿隨機矩陣(整數平手、
  大數值、±1000 附近、小值,1 到 7 行)對 tests/siege-game.js 的 gameFault 打 10 萬次:0 個錯。
- 一格 = 共軍的動作帶那個 plan 套用、國軍給那個回答、之後的 pending 照 bot 平常的回答(共軍的 −1 / +1
  照它自己評估最好的),再用做決定那一方的評估。共軍行動回合的格子加普通 / 困難本來的雜訊(0.6 / 0.2),
  候選的值 = 賽局值;pending 的回答(國軍答圍點打援、共軍在 ops pending 裡打城)本來沒有雜訊,照舊。
- 國軍的猜測裡暗牌被 view 蓋掉;每一列自己把 plan 放上去,所以回答只是 view 與 rng 的函數
  (B5 的對照、tuning/26/leak.mjs 200 局 922 次比較都是 0 個不同)。
- 困難:前 4 名重排時,打城候選 = Σ p_i q_j ×(那一格之後對手最好的一步)。
- 簡單:隨機玩家照舊抽,B 的兩個決定再照 EASY_SIEGE 改(0.8 打點、0.8 固守);random.js 沒動。
- 模擬的深處(評估別的候選時、困難的對手一步)沒有解賽局:打城展開成兩種 plan,模擬裡的國軍用對那個
  plan 最好的回答。這是近似,對攻方保守;只影響 bot 在想像中怎麼看打城,不影響真正的決定看不看得到暗牌。
